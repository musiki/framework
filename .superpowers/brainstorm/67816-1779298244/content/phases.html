Fases del sistema de notas

Los docs ya decidieron la dirección. ¿En qué orden avanzamos?

FASE 1 ~1 semana
Drop GitHub
El editor escribe .md directo al filesystem del VPS.
Sin GitHub App, sin PR, sin rebase.

API nueva:
• POST /api/notes/save
• POST /api/notes/create
• DELETE /api/notes/delete
• PATCH /api/notes/move

✓ Valor inmediato
Los .md siguen siendo el source de Astro
FASE 2 ~2 semanas
Editor UI
Mejoras al editor web:

• YAML autocomplete (chapter, type, status — valores de notas existentes)
• Crear nota nueva con modal
• Borrar nota con confirmación
• Tree view con drag-drop (reusar componente RECURSOS)
• Menú contextual click derecho
• Reordenar (edita order: en YAML)

✓ UX completa para teachers
FASE 3 ~2-3 semanas
Postgres + Version History
Lo que ya dicen los docs:

• Tabla course_notes en Postgres
• Cada save guarda snapshot (1 mes)
• UI para ver historial y restaurar versión
• Astro lee desde Postgres en runtime
• Obsidian sync: import/export vía API

✓ Alineado con class-workspace-refactor.md
Nota de los docs: class-workspace-refactor.md (2026-05-14) ya establece "Postgres is the canonical authority". Las fases 1 y 2 son el camino hacia eso, no contradicen la dirección.

¿Cuál es el scope del branch de hoy?

A

Solo Fase 1

API de escritura directa al filesystem. Sin editor UI nuevo todavía. Funcional en días.

B

Fase 1 + inicio Fase 2

API + tree view básico + crear/borrar notas. Sin Postgres todavía. Semana y media.

C

Todo en un branch

Las 3 fases. Más ambicioso, riesgo de quedar en un branch largo sin merge.
